## Design Specificity Verdict

**LLM assessment: high, and genuinely so — but the surface has drifted generic exactly where real data volume pushed back.**

This could not be lifted onto another product without a rewrite. `PANE_ORDER` (`src/lib/useKeymap.ts:22`) is named for one person's actual life. The hint codes in `src/config/defaults.ts:19` are their working stack — `gd Datasphere`, `gz Zeiterfassung`, `gp Proxmox`. `clock.secondary` carries `IBsolution / IST / UTC` because of an India team. `expectRunning: [100,101,104,105,111,112]` encodes which of *their* fourteen containers matter. `src/App.tsx:136` builds a per-guest noVNC console URL that is meaningless without a Proxmox node on the same LAN. And the interaction model is real tmux/ranger rather than a costume — the tell is `useKeymap.ts:177`, where any unclaimed letter falls into search. That is an fzf instinct, not a dashboard decision. Even the constraints are specific: no icon library, so states are `● ○ ! ━─ ▁▂▃`; `server/pve.ts:105` handles "zero vzdump tasks" first because that is true of this cluster.

Where it thins, it thins in three named places. The mockup encoded threshold color on the guest cells that matter (`mockup/index.html:490` — `<span class="val warn">94 %</span>`); the shipped table renders fourteen undifferentiated rows (`src/widgets/Homelab.tsx:66`), which is what any generic table does. `.pane--clip > .pane-body { height: 24rem }` (`src/index.css:91`) is a generic fixed-height scroll box, and it produces both the 370px void and an empty 24rem agenda — something no terminal multiplexer would ever render, because tmux panes fill their space. ## Overall Impression

This is a genuinely well-made thing with one structural failure repeated in two places, and it is the same failure both times: **the layout assumes more vertical room than the primary machine has, and nothing is sticky or scrollable to compensate.**

The consequence is perverse. A third of the visible viewport is empty background, while the command bar, the statusline, and the bottom of the homelab pane sit below the fold. The keyboard-first product's primary input is off-screen until a keystroke scrolls it there. Every piece of system state — mode, staleness, alarm count, error reason — is on the one strip you cannot see. And in the settings overlay the same arithmetic makes the Save button physically unreachable inside a `position: fixed` container with no scroller.

The single biggest opportunity: pin the statusline and command bar, drop the hardcoded `24rem`, and let the panes fill the space they already claim. That one change moves five heuristics at once, because it is not a styling problem — it is the reason a well-designed feedback system is invisible.

## What's Working

**1. The hint mechanic — `g` + two characters, printed inline next to its target.** It eliminates recall entirely by co-locating the shortcut with its destination, makes eighteen destinations two keystrokes deep, and is the reason the Links pane can be a dense text list instead of a tile grid. It is also the most product-specific thing in the codebase. `g` `d` → Datasphere is the moment this product earns its existence, and it works.

**2. The token discipline.** Eleven variables defined three times (dark default, `prefers-color-scheme: light`, `data-theme` override) and independently re-verified in `tests/contrast.test.ts`, so no component ever makes a color decision. The numbers hold under measurement: `--color-dim` on `--color-bg` ≈ 5.5:1, `--color-crit` on `--color-bg-sel` ≈ 4.5:1. Both themes stay legible with zero per-component work. This is the part most projects never get right.

**3. The failure semantics in the data layer.** `fetchNews`/`fetchEvents` throw only when *every* source fails (`src/widgets/News.tsx:25`, `src/widgets/Agenda.tsx:32`), with the reasoning written down. `emptyHomelab` separates "not configured" from "error". Both widgets separate "nothing configured" from "nothing found". Somebody thought hard about empty versus broken. The tragedy is that the presentation layer discards the distinction above the fold.

Worth crediting from Assessment B: **mobile does not break the box model.** At 375×812 horizontal overflow is exactly 0, all panes reflow to a 355px single column, and no pane is clipped vertically. The mobile damage is information loss through truncation, not layout collapse.

## Priority Issues

### [P0] Settings cannot be saved at 1280×800 with the real config

`.overlay` is `position: fixed; inset: 0` with `overflow-y: visible` (`src/index.css:243`). With the deployed four-group, sixteen-link config the `.set-box` measures **1068px inside an 800px viewport**; Speichern sits at y=1032 with no scroll container, and because the overlay is fixed, page scroll cannot reach it either.

**Why it matters:** the only exit is Esc or Abbrechen, both of which discard. The user cannot change any setting from their main machine. This is the worst state the product can reach, and it is reachable at the primary size on the primary device.

**Fix:** `.overlay { overflow-y: auto; place-items: start center; }` and make `.set-body` the scroller (`max-height: calc(100vh - 12rem); overflow-y: auto`) so `.set-head` and `.set-foot` stay pinned.

**Suggested command:** `/impeccable harden`

### [P0] Statusline and command bar are below the fold; all system feedback is invisible

Measured independently by both assessments. At 1280×720: document 1061px, `.cmd` top 974, `.statusline` top 1023. At 1280×800: document 1085px, statusline 1047–1075. Meanwhile ~370px of visible viewport is empty, because `.pane--tall` on Links (`src/App.tsx:286`) makes the left column two rows tall while `.pane--clip > .pane-body { height: 24rem }` (`src/index.css:91`) caps agenda and news.

**Why it matters:** the user cannot see staleness, alarms, mode, or whether a save landed — and the primary input of a keyboard-first product is off-screen until a keystroke scrolls it there. Pressing `6` makes it worse: `src/App.tsx:169` uses `focus({ preventScroll: true })`, so the pane you just focused stays off-screen and the strip that would confirm the focus move is off-screen too. It reads as broken.

**Fix:** make `.statusline` and `.cmd` `position: sticky; bottom: 0` — the statusline already has an opaque `--color-bg-sel` background. Drop the hardcoded `24rem` so agenda and news fill the row Links defines.

**Suggested command:** `/impeccable layout`

### [P1] Thirty-seven navigable rows and not one is a link or a button

`document.querySelectorAll('.app a').length === 0`. Links rows are `<li className="row">` with `cursor: auto` (`src/App.tsx:298`), news rows are `<div>`, guest rows are `<tr>`, and panes are `tabIndex={-1}` (`src/shell/Pane.tsx:23`) — so Tab reaches exactly one control on the entire dashboard: the command-bar input. The mockup's German pane `aria-label`s (`mockup/index.html:353`) were dropped, so no `<section>` is exposed as a landmark, and there is no `<h1>`.

**Why it matters:** mouse and touch users can open nothing. Screen-reader and keyboard-only users get inert text with no structure — and the only landmark inside a pane is `<nav aria-label="Links">`, which contains zero links. Nobody can middle-click, copy a link address, or see a target URL on hover.

**Fix:** render each row's target as a real `<a href>` filling the row, keeping `j`/`k` driving `.is-sel` and calling `.click()`. Restore the per-pane German `aria-label`. Add a visually-hidden `<h1>`.

**Suggested command:** `/impeccable harden`

### [P1] The homelab pane displays numbers it never evaluates

`torrent.local` at **95%** memory and `qbit.local` at 86% both render `class="val"` in plain `--color-fg` (`src/widgets/Homelab.tsx:66`) against a configured `thresholds.mem: 85` — byte-identical to `caddy` at 8%. The mockup specified `class="val warn"` for exactly these cells. Grepping `thresholds` across `src/` and `server/` shows `cpu` and `mem` are written by `src/shell/SettingsPane.tsx:418` and read **nowhere**; only `storage` and `backupAgeHours` reach `server/pve.ts`. The one alert that does fire ("31 updates verfügbar") is the last line of the last pane, below the fold, and its `!1` badge is on the invisible strip.

**Why it matters:** this is the pane's entire job. The user scans fourteen identical rows, concludes the lab is fine, and a container sits at 95%. The lab *looks* calm because nothing is evaluated. Two settings fields promise control they do not have. Separately, `.alert` uses the same `!` glyph for `warn` and `crit`, making severity color-only with no text alternative.

**Fix:** emit a per-guest level from `buildHomelab` — keeping the rule in `server/pve.ts` per AGENTS.md — and apply `warn`/`crit` to the `.val` cells. Add cpu/mem guest alert rules. Give the alert mark a text severity word alongside the glyph.

**Suggested command:** `/impeccable colorize`

### [P2] Feedback and destructive actions carry no weight

Every message renders by replacing the clock text (`src/shell/StatusLine.tsx:61` — no `role`, no `aria-live`) and auto-clears at 2500ms (`src/App.tsx:74`), including the 409 write conflict. `src/App.tsx:377` closes the settings overlay before the mutation resolves, so "Ein anderes Gerät hat zuerst gespeichert. Seite neu laden." — good copy — flashes off-screen with nothing left to retry from. `✕` deletes a link group with no confirm. `.rowact:disabled` has no styling, so dead arrows look live. The bangs `↑`/`↓` are wired to `onMove={() => undefined}` (`src/shell/SettingsPane.tsx:467`): two hover-responsive controls per row that do nothing.

**Fix:** `role="status" aria-live="polite"` on the note slot; never auto-clear a `crit` message; keep the settings overlay open until the mutation succeeds and preserve the draft on 409; two-step `✕` for non-empty groups; style `:disabled`; implement or delete the bang arrows.

**Suggested command:** `/impeccable clarify`

## Questions to Consider

1. The statusline carries every piece of system state and is off-screen by default. Should it be the thing that never scrolls — and the 90px clock the thing that does? What does this dashboard look like if the top 40px is the status bar and the giant clock is deleted?
2. Rows that look like links, read like links, and live in a pane called `Links` are inert `<li>`s. Is keyboard-only a stance or an accident of building the keymap first? If it is a stance, why is there a mouse-driven settings dialog?
3. `thresholds.cpu` and `thresholds.mem` are configurable and consumed nowhere. How many other settings does the user *believe* are wired up? What would this screen look like if every field had to cite the line that reads it?
4. The command bar shows six hits and can open only the first. Would showing exactly one — the hit Enter will actually open — be both simpler and more honest than a list promising reachability it does not have?
5. The homelab pane shows fourteen rows because Proxmox returns fourteen resources. For a page glanced at twenty times a day, what is the *smallest* thing that says "the lab is fine" — and would that let the pane collapse to one line until it is not?
